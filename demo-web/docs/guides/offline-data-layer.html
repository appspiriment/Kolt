Offline-First Data Layer

Hands-on architecture guide for implementing a local-first offline-capable data flow using SQLDelight and a synchronization queue.

Overview

Under Kolt's coding rules, the application must remain fully usable even without network connectivity. To achieve this, repositories expose local database streams as the sole data sources for ViewModels. Operations are performed locally first, and synchronization with a remote backend happens in the background.

UI / Presentation  ──► Repository Interface (Domain)
                             │
                             ▼
                 Repository Implementation (Data)
                 ├── Reads: SQLDelight Local Store (Flow)
                 └── Writes: SQLDelight + OfflineMutationQueue

Step 1: SQLDelight Schema Definition

Declare your local schema and query methods in a .sq file inside the Data module. SQLDelight will autogenerate type-safe query APIs:

// ProductDb.sq
CREATE TABLE ProductEntity (
    id TEXT NOT NULL PRIMARY KEY,
    name TEXT NOT NULL,
    price REAL NOT NULL,
    isSynced INTEGER NOT NULL DEFAULT 0
);

selectAll:
SELECT * FROM ProductEntity;

insertProduct:
INSERT OR REPLACE INTO ProductEntity(id, name, price, isSynced)
VALUES (?, ?, ?, ?);

markAsSynced:
UPDATE ProductEntity SET isSynced = 1 WHERE id = ?;

Step 2: Define Domain Repository Interface

Declare the repository interface inside your platform-independent Domain module. Notice that it works entirely with pure Kotlin types, exposing data streams via standard Flow:

// ProductRepository.kt (Domain Module)
interface ProductRepository {
    fun streamProducts(): Flow<List<Product>>
    suspend fun saveProduct(product: Product): AppResult<Unit>
}

Step 3: Repository Implementation (Data Module)

Implement the interface inside your **Data module**, linking the local SQLDelight store and enqueuing offline mutations for remote synchronization:

// ProductRepositoryImpl.kt (Data Module)
class ProductRepositoryImpl(
    private val dbQueries: ProductDbQueries,
    private val mutationQueue: OfflineMutationQueue,
    private val dispatchers: DispatcherProvider
) : ProductRepository {

    override fun streamProducts(): Flow<List<Product>> = 
        dbQueries.selectAll()
            .asFlow()
            .mapToList(dispatchers.io)
            .map { entities -> entities.map { it.toDomainModel() } }

    override suspend fun saveProduct(product: Product): AppResult<Unit> = safeCall(dispatchers.io) {
        // 1. Write locally first to ensure instant UI responsiveness
        dbQueries.insertProduct(
            id = product.id,
            name = product.name,
            price = product.price,
            isSynced = 0
        )
        
        // 2. Enqueue the mutation to be synchronized in the background
        mutationQueue.enqueue(
            SyncMutation(
                type = MutationType.UPSERT,
                payload = product.toJsonString()
            )
        )
    }
}

Step 4: Background Sync Engine

The background SyncEngine runs asynchronously, draining the queue and uploading mutations to the remote source. Once a mutation completes successfully, the item status is marked as synced:

// SyncEngine.kt
class SyncEngine(
    private val mutationQueue: OfflineMutationQueue,
    private val remoteSyncSource: RemoteSyncDataSource,
    private val dbQueries: ProductDbQueries
) {
    suspend fun drainQueue() {
        mutationQueue.streamPendingMutations().collect { mutation ->
            val success = remoteSyncSource.uploadMutation(mutation)
            if (success) {
                // Mark entity as synchronized locally
                dbQueries.markAsSynced(mutation.entityId)
                mutationQueue.dequeue(mutation.id)
            }
        }
    }
}
